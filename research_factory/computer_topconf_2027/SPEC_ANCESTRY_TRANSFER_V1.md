## 1. Target residual abstraction

2026 pressure:
- formal code generation is increasingly bottlenecked by specification quality rather than syntax alone;
- equivalent final requirement contracts can yield different agent outcomes depending on revision history;
- spec-driven systems are beginning to compile requirements and code graphs into context for agents.

Abstract problem:

authoritative input state S
->
derived computation/artifacts D
->
input change delta S
->
which parts of D are invalid and must be recomputed so that the final observable result is equivalent to a clean computation from the new authoritative state?

This abstraction removes "LLM" and "requirements" and exposes a mature computer-science problem:
**incremental recomputation under changing authoritative inputs with dependency-aware reuse and from-scratch consistency.**

The central target difference:
in classic systems dependencies are explicit/deterministic.
In coding agents, important dependencies are semantic, cross-artifact, and partially generated by the agent itself.

# 2. Ancestor A — Program Slicing / Change-Impact Analysis

## Source structure

SOURCE_STATE:
program statements, variables, procedures and dependence graph.

SOURCE_CHANGE:
a changed statement/input/variable or a slicing criterion.

SOURCE_INVARIANT:
the impacted slice must include every statement that can affect the criterion.

SOURCE_OPERATOR:
reachability over control/data dependence graph; interprocedural slicing; forward impact analysis.

SOURCE_GUARD:
dependencies are represented sufficiently accurately.

SOURCE_FAILURE_MODE:
coarse dependencies over-approximate and cause large slices; missing dependencies create unsound slices.

SOURCE_EVIDENCE:
slice coverage/soundness and reduction in analyzed code.

## Target mapping

program statement
-> requirement/spec atom, design decision, plan step, test, code artifact.

data/control dependence
-> "this derived artifact/decision was justified by or semantically depends on this requirement/decision."

changed slicing criterion
-> changed/retracted requirement.

impacted slice
-> artifacts that must be invalidated/rechecked/rederived.

## Broken target assumptions

1. Target dependencies are not all syntactic.
2. The agent may create latent decisions without explicit provenance.
3. Natural-language requirements can imply semantic dependencies across code far from direct references.
4. Multiple artifacts can be alternative derivations rather than deterministic nodes.

## Mismatch residual

Classic slicing asks:
"given a dependence graph, what is affected?"

Coding agents additionally require:
**how do we discover a sufficiently sound semantic derivation graph in the first place?**

## Transfer hypothesis A1 — Behavioral Derivation Slice

Require coding agents to emit minimal explicit provenance edges:
requirement -> decision -> verification obligation/test -> implementation artifact.

On requirement change:
compute the transitive impacted slice and only re-open those derived nodes.

Prediction:
a sound derivation slice should recover revision-path invariance with substantially less recomputation than full reset.

Cheap falsifier:
use contract-equivalent revision tasks:
- direct consolidated final spec;
- raw revision-history baseline;
- full reset/replan on final spec;
- dependency-sliced rederive.

Evaluate final verifier outcome and recomputation fraction.

Kill if:
path invariance requires nearly full invalidation, or dependency omissions dominate.

Verdict:
TRANSFER_OPEN IN PRINCIPLE, but current tools such as SpecD already perform spec/code graph impact analysis, so "dependency graph + impact" alone is not novel.

# 3. Ancestor B — Self-Adjusting Computation

This is the strongest mature ancestor found so far.

## Source structure

SOURCE_STATE:
input/memory plus a dynamic dependence graph (DDG) recording which computation consumed which data.

SOURCE_CHANGE:
external mutation to input/state.

SOURCE_INVARIANT:
after change propagation, the result should match a fresh execution on the changed input.

Canonical property:
**from-scratch consistency.**

SOURCE_OPERATOR:
record dynamic data/control dependencies during execution;
mark affected computation stale;
selectively re-execute affected nodes;
reuse unaffected results;
update the dependence graph as execution changes.

SOURCE_GUARD:
dependencies are captured correctly; computation structure exposes appropriate granularity.

SOURCE_FAILURE_MODE:
if dependency granularity is poor, change propagation approaches full recomputation;
if dependencies are missing, reuse becomes unsound;
dynamic/cyclic/side-effectful computations require stronger semantics.

SOURCE_EVIDENCE:
observational equivalence to from-scratch execution plus work saved by selective recomputation.

## Target mapping

source input
-> active requirement/specification state + repository state.

source computation node
-> derived agent decision / plan / test / edit / summary / tool result.

source DDG
-> behavioral derivation graph.

source changed memory
-> requirement revision/retraction/replacement.

source change propagation
-> selective invalidation + re-planning/re-testing/re-editing.

source from-scratch consistency
-> final behavior should match a fresh agent run from the consolidated final authoritative specification, modulo stochastic tolerance defined by verifier behavior.

## Broken target assumptions

This is exactly where the research opportunity appears:

1. Dependencies are semantic and uncertain, not explicit memory reads.
2. Agent execution is stochastic and non-deterministic.
3. "Same result" cannot generally mean byte-identical code; it must mean behavioral/specification equivalence.
4. Derived state spans heterogeneous layers: plan, tests, code, summaries, tool state.
5. The agent can invent a dependency it never records.
6. Re-running an affected node can itself discover new dependencies.

## Mismatch residual

Classic self-adjustment:
**exact dependency graph + deterministic change propagation -> from-scratch consistent incremental result.**

Coding-agent regime:
**uncertain semantic dependency graph + stochastic rederivation -> need probabilistic/behavioral from-scratch consistency.**

This mismatch is substantially more interesting than generic "minimal specification".

## Transfer hypothesis B1 — From-Scratch Consistent Agent Updates

Maintain an explicit derivation graph while the coding agent works.

When requirements change:
1. compute affected derived-state closure;
2. invalidate/rederive only that closure;
3. preserve unaffected state;
4. require final verifier behavior to match a clean run from the consolidated final spec.

Primary research claim would not be "save tokens".
It would be:

**dependency-scoped rederivation can make coding-agent behavior path-invariant under requirement evolution while avoiding full replay.**

Two endpoints are both load-bearing:
- behavioral consistency with clean-from-scratch final-spec execution;
- recomputation/token/tool-call fraction.

Cheap falsifier:
SpecPath-style equivalent histories with a frozen coding agent.
Implement only external provenance/invalidation orchestration first; no model training.
Compare:
A. raw history;
B. current-context refresh only;
C. full restart from final spec;
D. dependency-scoped rederive.

If D cannot approach C's behavioral consistency while materially reducing work, kill this transfer.

Verdict:
HIGH-VALUE TRANSFER, but target occupancy is already pressured by PlanFence and SpecD and needs exact boundary adjudication.

# 4. Ancestor C — Incremental View Maintenance / Provenance

## Source structure

SOURCE_STATE:
base relations + derived/materialized views.

SOURCE_CHANGE:
insert/delete/update delta to base data.

SOURCE_INVARIANT:
derived view after incremental maintenance equals the result of recomputing the view over the updated base state.

SOURCE_OPERATOR:
derive view delta from base delta and query/provenance structure; apply only delta rather than recompute full view.

SOURCE_GUARD:
query semantics/dependency lineage is known.

SOURCE_FAILURE_MODE:
recursive/nonlinear aggregation and high fan-out can make incremental maintenance complex or expensive.

## Target mapping

base relation
-> authoritative requirement/spec facts.

materialized view
-> derived plan/tests/code assumptions.

data provenance
-> requirement/decision provenance.

base delta
-> requirement update.

view delta
-> changes to derived artifacts.

## Broken assumptions

Agent-derived artifacts are not pure deterministic query results.
A changed requirement can alter the agent's future search/implementation choices, not just update values.

## Mismatch residual

Need a provenance model for **decision-generating computations**, where a small upstream change may cause a branch change in downstream reasoning.

## Transfer hypothesis C1 — Spec Delta / Artifact Delta Algebra

Represent requirement changes as explicit add/remove/replace deltas and propagate them through typed derived artifacts instead of replaying the full history.

Potential contribution:
a typed delta semantics for requirement -> obligation -> test -> implementation.

Risk:
this may become PL/formal-method work and requires rigorous semantics; a shallow implementation overlaps spec-driven development tools.

Verdict:
WATCHLIST / likely PLDI-shaped only if formalized strongly.

# 5. Ancestor D — Build Systems / Incremental Compilation

## Source structure

SOURCE_STATE:
source files/artifacts + dependency DAG.

SOURCE_CHANGE:
file/config change.

SOURCE_INVARIANT:
rebuild every artifact whose result can be affected; reuse the rest.

SOURCE_OPERATOR:
dependency tracking, invalidation, content hashing, build graph scheduling.

## Target mapping

build artifact
-> agent-derived artifact.

dependency DAG
-> requirement-to-artifact derivation graph.

rebuild
-> rederive/reverify.

## Key transfer lesson

A timestamp/freshness check is insufficient; correct reuse depends on dependency identity and content semantics.

This directly mirrors the agent problem:
"memory is fresh" does not imply a derived plan remains valid.

However, PlanFence already applies dependency-scoped validation to stale agent plans.
Therefore generic stale-plan invalidation is occupied.

Verdict:
SOURCE LESSON retained; not a standalone candidate.

# 6. Target occupancy boundary

## Current direct/adjacent target work

### SpecPath
Establishes the pressure:
contract-equivalent requirement histories can lead to different coding-agent behavior.
It is diagnostic, not a selective rederivation method.

### VeriEquivBench
Establishes specification-quality evaluation as a major bottleneck for formally verifiable code.
It focuses specification equivalence/evaluation, not revision-path incremental consistency.

### Intent Formalization
Explicitly frames intent-to-checkable-specification and compositionality over changes as open challenges.

### PlanFence
Very important occupancy boundary:
plans cite exact records; executors validate only records that can affect the pending action; stale dependency causes replanning/blocking.

Therefore DO NOT claim:
"first dependency-scoped stale-plan validation for agents."

### SpecD
Engineering tool already exposes:
- compiled spec context;
- spec/code graph;
- impact analysis;
- deterministic delta application.

Therefore DO NOT claim:
"first spec graph / impact analysis for coding agents."

## What may remain open

The stronger contract is:

**record semantic derivation during agent execution and guarantee/measure from-scratch behavioral consistency after requirement revisions via selective rederivation across heterogeneous artifacts.**

Distinct axes:
- consumer: coding-agent implementation under evolving requirements;
- state: runtime derivation lineage spanning requirement -> decision -> test -> code;
- intervention: selective invalidation/rederivation, not only pre-action validation or context compilation;
- evidence: equivalence/path-invariance to clean final-spec execution + saved recomputation.

This exact A/B/C/D contract still requires bounded direct-prior search before activation.

# 7. Cross-ancestor invariant

Program slicing, self-adjusting computation, databases and build systems converge on one principle:

> **Reuse is correct only when you can prove that reused derived state is independent of the changed authoritative state.**

Equivalently:

freshness != validity.

The transferable structure is:

authoritative state
->
recorded derivation/dependency
->
upstream delta
->
affected closure
->
selective invalidation/recompute
->
from-scratch consistency check.

This is substantially stronger than:
"give the agent a cleaner spec."

# 8. Strongest target hypothesis after transfer

Working object:

## Behavioral Self-Adjustment for Coding Agents

A coding-agent run constructs a **Behavioral Derivation Graph (BDG)** whose nodes include:
- active requirements;
- explicit design decisions;
- verification obligations/tests;
- implementation changes;
- externally visible actions.

Edges mean:
"the downstream artifact/action may become invalid if the upstream node changes."

On a requirement revision:
- invalidate the transitive affected closure;
- rederive only that closure;
- preserve independent work;
- compare final behavior against a clean run from the consolidated final specification.

Core invariant:
**Behavioral From-Scratch Consistency (BFSC)**

An incremental/revision-history run is correct when the verifier-observable behavior is equivalent to the clean final-spec run under the frozen behavioral equivalence contract.

This is the current strongest cross-domain transfer from the niche scan.

# 9. Negative transfer / likely failure

The biggest risk is not implementation complexity.
It is that semantic dependency discovery is too unreliable.

If dependency recall must approach 100% and the only safe strategy is to mark almost everything dependent on everything, selective rederivation collapses to full restart.

Reality if this transfer is wrong:
- path-invariance improves only when invalidating nearly all prior work;
- missed semantic dependencies produce silent behavioral divergence;
- graph construction overhead exceeds saved recomputation;
- clean consolidated-spec runs remain clearly better and simpler.

This is an excellent falsifier because it can kill the idea without model training.

---

# 10. Cheapest experiment implied by ancestry

Do NOT first train a dependency model.

Use a small controlled coding-agent benchmark with equivalent requirement histories.

For every task:
1. run a clean consolidated final specification (gold behavior reference, not gold code);
2. run revision history normally;
3. instrument the agent to externalize requirement/decision/test/code provenance edges;
4. introduce a final revision;
5. compare:
   - keep all prior state;
   - full reset/replay;
   - naive changed-file/spec retrieval;
   - dependency-scoped rederivation.

Measure:
- verifier-equivalent final behavior to clean run;
- invalid action / stale decision rate;
- fraction of prior derived nodes invalidated;
- tokens/tool calls/wall-time;
- dependency precision/recall on controlled known-change cases.

One experiment can answer the key economic question:
is there a nontrivial regime where BFSC is achievable without near-total replay?

# 11. Venue fit

If the contribution is:
- formal semantics of BDG/BFSC + correctness conditions + implementation:
  PLDI-style fit is plausible; PLDI 2027 research deadline is 2026-11-12.

If the contribution is:
- empirical coding-agent orchestration with provenance/invalidation:
  software-engineering venues are more natural; FSE 2027 is too near for a fresh full paper in this cycle, and ICSE 2027 research submission is already closed.

If the state/invalidation principle generalizes beyond coding agents:
  broader ML/AI fit could reopen, but that is not assumed.

Do not force this into ICML/NeurIPS merely because the project started as ML topic selection.
