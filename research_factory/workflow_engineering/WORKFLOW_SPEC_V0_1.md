## 1. 目标、判断及可推翻条件

目标是让同一套工作流可重复执行真实复杂任务，并能追溯何处产生收益、错误和返工。先工程化，后回顾历史，再进行受控比较；不把“拼了几篇顶会论文”本身当贡献。

当前判断：最小可用组合不是同时运行多个论文的优化器，而是把任务执行、工作流改进、证据验收分开。它们共享明确接口，但不能互相越权。

观察依据：本地已有总计划、任务初始状态、回放协议、会话迁移和结果核算资产，但当前入口仍绑定旧科学课题；论文实现分别优化模块、任务图或工作流版本，作用对象不同。见第 3、8 节。

反例：若规范执行所增加的建模、调度、检查成本超过减少的错误/返工，或模块化导致必要上下文丢失、终点质量下降，这个实现就不值得保留。不能用“它更正交”来替代任务收益。

## 2. 固定什么，允许改变什么

固定的是：工作流版本、权限与接口、证据要求、允许的状态转换、一次只推进一个决策步骤、版本升级和终止规则。

允许改变的是：任务特定的依赖图、具体下一步、尚未证实的科学假设。改变必须按固定规则进行，而不是每轮临时发明规则。

任务计划的更新不等于工作流算法更新：
- 在同一已冻结的决策规则下，因为新证据改变任务图或下一步，属于正常执行。
- 改变分解/调度/记忆/验收算法，属于新工作流版本，不能在一场已计分的比较中偷偷替换。
- 改变根目标或反转研究方向，终止旧总计划并建立新计划；不以新名称伪装旧方案成功。

本轮终止的是旧 BFSC 执行总计划的继续授权，原因是用户转向工作流工程。BFSC 科学结论仍为未完成裁决，既不算被证伪，也不算新工作流的正面证据。

## 3. 已核验的机制，以及本次真正采用的部分

### S1｜AgentSquare，ICLR 2025：可替换模块接口

论文将 planning / reasoning / tool use / memory 定义成有统一输入输出的模块，并明确使用 orthogonal 的表述；模块重组与新模块生成在其设计空间中搜索。[S1]

公开 workflow.py 显示规划后按子任务顺序执行，在环境中调用工具和推理，并在成功时更新记忆。因此四个模块不等于四个可以同时独立运行的 worker；标准化接口也不是行为无干扰证明。[S1-code]

采用：每个能力都必须声明输入、输出、依赖和允许影响的资源，使替换可比较。
不照搬：固定四个角色名称、把每个角色都开成子 agent、没有反馈校准就用代理预测分数代替真实结果。

### S2｜Flow，ICLR 2025：任务依赖图与局部重规划

论文以任务依赖图组织执行，考虑并行度、依赖复杂度，并在执行反馈后调整图。[S2]

公开 workflow.py 有任务 objective / prev / next / status / history 等字段；get_context 汇集已完成的前置任务结果，merge_workflow 会增加、编辑、删除任务。workflowManager.py 将当前图交给模型调整。[S2-code]

重要实现差异：论文描述按并行度、依赖复杂度选择图；当前公开 main 的 compare_results 使用两项标准化量之差评分。这个 main 不能不经锁版本与复现就当成论文实验的精确实现。公开代码的“completed”状态也不能直接代替我们自己的证据验收。

采用：显式依赖图、就绪任务调度、在证据变化后局部更新计划。
不照搬：默认一次生成 10 个候选图、把结构并行度当最终质量、自动一直执行到整个任务结束。不能为了减少边而删除真实依赖。

### S3｜AFlow，ICLR 2025：工作流版本的执行反馈与演化

AFlow 搜索的是代码表示的工作流。公开 optimizer.py 选择历史版本，读其代码、经验和失败反馈，生成修改，执行评价，再积累经验。[S3]

采用：保存父版本、精确改动、执行结果和预算；证据驱动地局部改进工作流，而不是每轮全部重写。
不照搬：在缺少可信终点评价时运行多轮搜索、重复生成直到通过、把搜索开销排除在成本之外。仓库 README 对迁移后的部分 operator 有缺陷风险提示。[S3-code]

这里是外层“改进做事方法”的循环，不是内层“完成一次用户任务”的循环。

### S4｜A²Flow，AAAI 2026：从实际案例形成候选操作

论文先从专家示范提取具体操作，再功能聚类、多路径多轮抽象，形成供工作流搜索使用的操作，并引入历史输出记忆。[S4]

采用：在开发历史中找到重复出现且已经有实际产物的动作，形成候选能力卡；复用前检查适用条件和失败边界。
不照搬：只读成功论文叙事就认定抽出了可靠操作、所有历史全部塞给每个节点、把 Python 可执行等同任务正确。

实现限制：本轮查看论文关联的 pandawei-ele/A2FLOW 仓库，公开 main 仅列 README，没有可直接替换的 operator 实现。[S4-code] 因此这里只是机制借鉴，不是官方代码复用或 A²Flow 复现。能力抽取默认不在每次新任务开始时运行，只有重复瓶颈值得固化时才进入离线改进。

### S5｜EnCompass，NeurIPS 2025：把任务逻辑与搜索策略分开

论文通过带分支点的程序及可恢复状态，使任务逻辑与搜索策略分离。[S5]

采用：任务代码不直接决定探索几个分支、何时重试或何时停止；这些由外层预算和授权策略控制。
不照搬：立即接入新编译器、把内存状态恢复当成文件/数据库/外部服务已回滚。需要真实副作用隔离时，必须另有工作区和权限控制。

作者主页所链接的 GitHub 地址本轮重定向到 OpenEncompass，其 README 自称论文的一种实现；本轮未建立它与论文实验代码的同一性，因此不纳入已验证运行时代码资产。

### 小结：不是五个优化器串联

执行主干借 S1+S2；外层版本改进借 S3；经验形成借 S4；两类循环的边界借 S5。没有证据要求时，搜索、抽取和并行均可关闭。ADAS、MaAS、MLE-STAR 等不进入 v0.1 核心；本轮没有完成它们的实现级核验。

## 4. 唯一执行主链

任务目标与验收冻结
→ 恢复已有有效资产
→ 总计划 + 一个当前决策步骤
→ 建立当前步骤的依赖与模块接口
→ 只运行当前步骤内已就绪的工作单元
→ 收取产物并重读权威状态
→ 检查有效性并作出有边界的结论
→ 保持 / 修改 / 终止总计划，写一个 NEXT_STEP
→ STOP

一个“步骤”是能回答一个明确问题、改变一个明确决策的有界工作包，可以包含必要的检索、代码检查、多个工具调用和至多两个独立工作单元。不能把整个课题藏在“一步”里，也不能机械地把一个工具调用当成一个科研步骤。

NEXT_STEP 是计划，不是自动授权。更长周期的调度器必须另行获得授权；本规范不修改 Watchdog、不自动挂载、不创建后台推进。

## 5. 四个接口，不再增加一套空泛角色

| 对象 | 最低必需内容 | 不拥有的权限 |
|---|---|---|
| TaskContract | 真实目标、初始输入引用/哈希、资源上限、终点评价、硬限制、停止条件 | 不凭运行结果改评价 |
| PlanStep | plan/version、当前问题、依赖、允许动作、交付物、接收条件、预算 | 不把列出的后续动作自动授权 |
| OperatorSpec | 输入/输出类型、读写范围、前置条件、产生的外部影响、检查方法、失败处理 | 不自行扩大任务或改全局状态 |
| StepReceipt | 对应步骤和版本、实际产物引用、观察/测试、资源消耗、异常、结论范围、下一步建议 | worker 自报成功不直接成为最终结论 |

语义尚未知允许显式标 UNKNOWN，例如“这个机制是否有效”；但执行目标、允许资源、评价对象不能缺失。禁止因为无法预知整个研究的所有接口，就无限停留在计划阶段。

状态分开保存：执行是否结束、证据是否有效、科学结论是否支持、计划是否继续是不同维度。执行失败/来源不合法不能记成科学反例；执行成功也不能自动记成方法有效。

## 6. 正交拆解、并行与不变量的实际含义

### 6.1 不把“拆成很多块”当作正交

模块应围绕可独立交付、可独立检查、可独立替换的产物拆分。必要依赖保留。例如基线实现复核与文献占位调查通常可以产出独立报告；某方法实验依赖基线已就绪，不能假装二者无依赖并行。

每个单元先声明读集 R 和写集 W。两单元并行的保守条件：双方均无尚未完成的依赖，且 W_i 与 R_j/W_j 无交叉，反向亦然；或者使用已验证的只读快照和各自隔离输出。未声明的外部服务、缓存、会话和绝对路径仍可能造成共享影响，所以声明本身不构成形式化证明。

共享权威文件只允许协调者写。worker 只交付自己的产物或修改建议。合并前重新检查当前计划版本和输入是否变化；不能用已经过期的计划覆盖新状态。

### 6.2 固定六类约束

1. **身份**：没有当前 plan/step/workflow/task 版本，不准启动计费或改变任务状态的执行。
2. **授权**：动作必须属于 CURRENT_STEP；预算与停止条件不得由 worker 扩张。完成后必须先提交证据、更新计划并停止。
3. **依赖/隔离**：前置产物尚未有效、读写冲突未隔离、会话仍指向源工作区时，不准调度或提交。
4. **证据**：摘要、退出码、日志消息和文件存在分别只能证明其实际内容；必须读取任务要求的最终权威状态。总计数包含失败尝试与实际重试。
5. **比较**：同任务的基线与新流程共用任务定义、可见信息和方法无关评价；运行中不能改测试集或用工作流自身的指标裁判它胜出。
6. **变更**：科学负例只淘汰已验证的假设范围。改总目标终止原计划；改工作流规则开新版本；历史记录和原比较保留。

自动检查只能覆盖结构、文件、哈希、预算等可编码性质。研究问题是否有价值、分解是否遗漏必要语义需要证据和人工/独立审查，不能把所有文字判断包装成自动证明。

### 6.3 最小反例集合（供下一步实现，不是本轮测试结果）

- plan 缺失或 receipt 的 plan 版本过期：必须拒绝启动/提交。
- 一个依赖环，或引用不存在的前置任务：必须拒绝图。
- 两 worker 写同一权威文件，或读取对方未提交的结果：必须拒绝并行。
- 会话中工具绝对路径仍指向原实验臂：必须阻断正式回放。
- 收到 terminal 日志但指定产物缺失/哈希不符：不得记为完成。
- 错误执行/缺文件：INVALID，不得记成科学 FAIL。
- evaluator/任务输入在运行后改变：旧 run 保留，变更建立新 run。
- receipt 已提交后重复提交或再次自动启动 NEXT_STEP：必须拒绝或幂等返回既有结果。
- 合法独立的两份只读调查：可以在同一 CURRENT_STEP 内并行，不能被过度保守的规则误拦。

## 7. 历史任务：先诊断，后同任务比较

第一层为 DEVELOPMENT_RETROSPECTIVE：利用真实历史输入、过程、产物和已知结局，定位状态越权、依赖遗漏、无效实验误判等错误。允许看结局，但必须打上开发标签，不能宣称“新流程当时本来会成功”。

第二层为 MATCHED_REPLAY：冻结原始任务及双方初始快照，在独立会话/工作区使用相同模型、工具和预算重跑旧工作流与新版本。不是拿旧日期/旧模型的历史费用直接与现在费用比较。固定的任务修订必须双方同样可见；真实环境中的查询顺序允许由工作流不同而不同，但不能把不同权威需求当成方法效果。

本对话已看过大量历史结局，无法靠声明“忘记答案”消除污染。正式执行需新上下文、输入白名单、隔离结果目录和检索范围；用于设计的历史保留为开发集。后续有效性确认仍需没用于修改流程的任务，必要时采用前瞻任务。

比较主指标由任务决定：终点正确性/质量与实际交付为主，成本、墙钟时间、返工及回归错误为辅；报告资源权衡，不用“正交分数”“不变量条数”直接评胜负。第一次离线检查仅验证门能否工作，不是论文实验。

若以后要归因于正交性或不变量，应以同一整合骨架只更换相关机制，并区分必要的实验完整性保障与被测试的算法干预。整体混合流程胜出不能自动证明其中某个组件贡献。

当前未挑选“容易赢”的新任务；先使用已有失败记录检验控制约束，再按原始状态是否可还原、真实复杂度和评价完整性冻结共同任务。BFSC 的 R0/R3 是其旧方法臂，不能改标签当作本工作流 A/B 结果。

## 9. 工程落地方案与本轮完成边界

拒绝方案 A：把多个论文框架完整堆叠。原因是优化对象、环境和迭代层级不同，会产生重复搜索、预算放大和状态归属冲突。
拒绝方案 B：只写一段“请遵守流程”的提示词。它不能在真实启动入口阻断越权执行。
选择方案 C：保留已有执行工具和任务资产，增加最小的版本化任务契约与准入/提交适配层；后续仅在真正需要的地方引入已有图调度或模块实现。

本规范冻结时实际落地：总计划和本文规范；AGENTS / 项目恢复入口指向本计划。它们对项目内后续代理行为是明确约束。
